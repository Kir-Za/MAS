# ADR Модель идентичности ingestion-сущностей

**Статус:** Принят

## Контекст

AI Crawler получает данные из Git, Confluence и Jira для хранения в Qdrant и Neo4j — двух проекциях общего домена, обновляемых без общей транзакции. Источники предоставляют разнородные внешние идентификаторы: одни идентифицируют устойчивый объект (Confluence `page_id`, Jira issue key), другие — ревизию (commit SHA). Смешивание этих категорий ведёт к ошибочным попыткам присвоить постоянную сущностную идентичность тому, что по природе является ревизией.

Требуется единая модель идентичности для кода, Confluence и Jira, которая разделяет идентичность сущности, идентичность версии и идентичность поискового фрагмента, однозначно определяет состав вычисляемых metadata-полей (`content_hash`, `derived_key`) для каждого источника.

## Решение

### 1. Типы объектов

Confluence page, Jira issue, Git branch, Git commit и code entity — разные типы объектов с собственными идентификаторами, связанные отношениями, а не альтернативными формами одного `entity_uid`.

### 2. Canonical Identity Resolver — общий компонент

Единственная точка выдачи `entity_uid`, регистрации `entity_alias`/`entity_redirect` и решений по версионированию сущностей. Canonical Identity Resolver, общий компонент расположенный до RAG и Graph. Обе ветви получают уже разрешённый `entity_uid`.

### 3. `entity_uid`: присвоение и уровни подтверждения

`entity_uid` — глобально уникальный идентификатор. Подтверждённый `entity_uid` никогда не пересчитывается. Присвоение новому наблюдению может быть по нескольким причинам, что отражается в статусах:

```text
CONFIRMED_BY_RULE    — evidence критерии;
CONFIRMED_BY_SOURCE  — источник сам предоставляет устойчивый идентификатор непрерывности объекта (объекты в Confluence при отсутствии конфликтов по копиям содержимого страниц);
AMBIGUOUS            — нет возможности определить статус, сделать вывод о принадлежности к entitiy_uid;
CONFIRMED_BY_HITL    — подтверждено вручную после AMBIGUOUS.
```

Для initial load: `CONFIRMED_BY_RULE` с пометкой `is_initial_baseline=true` только при выполнении минимальных условий; сущности неясного происхождения — `AMBIGUOUS`.

#### Evidence для кода

| Evidence | Вес | Что подтверждает |
|---|---|---|
| Совпадение `content_hash` с известной версией существующего `entity_uid` | 5 | Это та же сущность в том же состоянии |
| Совпадение `derived_key` (путь + qualified_symbol + symbol_kind + signature_fingerprint) | 4 | Сущность не изменила имя и положение |
| LSP: references, callers/callees совпадают с известной сущностью | 4 | Семантическая связь сохранилась |
| Git-история: один символ исчез, другой появился в том же или соседнем коммите | 3 | Вероятный rename/move |
| Близость `content_hash` (неполное совпадение) | 3 | Вероятный split/merge |
| Совпадение имени файла или имени символа без остального `derived_key` | 2 | Только косвенное указание |
| Отсутствие конкурирующего кандидата | 1 | Нет конфликта (необходимое, но не достаточное) |


#### Evidence для Confluence

| Evidence | Вес | Что подтверждает |
|---|---|---|
| Совпадение `page_id` и `space_key` | 5 | Та же страница в том же пространстве |
| Совпадение `content_hash` с известной версией | 4 | То же содержимое — вероятно та же страница (если `page_id` изменился при миграции) |
| Совпадение заголовка + структуры (иерархия заголовков, таблицы) при разном `page_id` | 3 | Страница могла быть перенесена между spaces |
| Запись в Confluence audit log о перемещении/миграции | 3 | Административное подтверждение |
| Совпадение labels/тегов | 2 | Косвенное указание |
| Совпадение автора и даты создания | 2 | Косвенное указание |
| Отсутствие конкурирующего кандидата | 1 | Нет конфликта (необходимое, но не достаточное) |


#### Evidence для Jira

| Evidence | Вес | Что подтверждает |
|---|---|---|
| Совпадение `issue_key` | 5 | Та же задача |
| Совпадение `content_hash` (снимок отслеживаемых полей) с известной версией | 4 | Задача в том же состоянии |
| Ссылка на issue_key в связанных объектах (коммит, ветка, PR) | 3 | Кросс-источник подтверждение |
| Совпадение summary при разном issue_key (миграция между проектами) | 3 | Задача могла быть перенесена |
| Jira issue migration log | 3 | Административное подтверждение переноса |
| Отсутствие конкурирующего кандидата | 1 | Нет конфликта (необходимое, но не достаточное) |

### 4. `derived_key` по источникам

`derived_key` — мутируемый ключ-кандидат, используемый **только внутри resolution pipeline**; никогда не публикуется как идентификатор сущности.

```text
Код:
  derived_key = repository_id + module_path + qualified_symbol
               + symbol_kind + signature_fingerprint

Confluence:
  derived_key = space_key + page_id

Jira:
  derived_key = issue_key
```

`signature_fingerprint` включает арность, variadic-признаки, generic-арность и типы параметров (при доступности статической типовой информации), исключает имена параметров. Для Confluence/Jira source сам гарантирует устойчивость идентификатора (`page_id`, `issue_key`), поэтому резолюция для них, как правило, `CONFIRMED_BY_SOURCE` — в отличие от кода, где отсутствие native persistent symbol ID требует evidence-based `CONFIRMED_BY_RULE`/`CONFIRMED_BY_HITL`.

`entity_alias` — запись о том, что определённый `derived_key` или внешний идентификатор когда-то принадлежал данному `entity_uid`.

`repository_id` - id repository at BitBucket.

`module_path` - Путь к файлу относительно корня репозитория, с заменой разделителей на точки и без расширения.

`qualified_symbol` - Полное имя символа, включающее класс-родитель при его наличии. Извлекается через LSP.

`symbol_kind` - Тип символа по классификации LSP: `function`, `method`, `class`, `interface`, `enum`.

`issue_key` - Уникальный идентификатор задачи в Jira, присвоенный при создании. 

`space_key` - Уникальный идентификатор пространства в Confluence.

### 5. Область уникальности, fork и миграция

- **Переименование/разделение/слияние репозитория** с сохранённой git-историей сохраняет `entity_uid` через `entity_alias` при подтверждённом lineage.
- **Перемещение Confluence-страницы** внутри space с сохранением `page_id` не меняет `entity_uid`. **Миграция между spaces/сайтами** — resolution decision через HITL; старый идентификатор сохраняется как `entity_alias`.
- **Перенос Jira issue между проектами** (со сменой `issue_key`) обрабатывается аналогично rename кода: при наличии в источнике записи о переносе (историческая ссылка на старый key) — `CONFIRMED_BY_SOURCE`, старый key — `entity_alias`; при отсутствии такой записи — `AMBIGUOUS`/HITL.

### 6. Идентичность содержимого: `entity_version_id` и состав `content_hash`

```text
entity_version_id = hash(entity_uid + content_hash)
```

Повторное наблюдение идентичного `content_hash` распознаётся как одна `entity_version_id` — дедупликация контента без потери истории наблюдений.

**Состав `content_hash` по источникам:**

- **Код:** `full_symbol_span_text` (включая сигнатуру), `module_path`, `declared_interfaces_or_base_types`.
- **Confluence:** нормализованный текст, заголовки и иерархия, таблицы, списки, макросы, ссылки, структурные anchors, диаграммы и вложения. Служебные поля (счётчики просмотров, last viewed) не входят.
- **Jira:** снимок всех отслеживаемых полей на момент изменения. Один changelog-batch (все поля, изменённые одной операцией) образует один снимок и одну `entity_version_id`.
- **ADR** только текст документа. Статус не входит в `content_hash` — это метаданные, а не контент; смена статуса без изменения текста не создаёт новую `entity_version_id`.

`full_symbol_span_text` — полный текст кодовой сущности, включающий сигнатуру и тело, извлекается LSP как текстовый диапазон от начала объявления символа до его конца.

`declared_interfaces_or_base_types` — список интерфейсов, которые класс реализует, и базовых классов, от которых он наследуется, извлекается LSP из объявления класса.

### 7. `entity_revision_observation` — базовая схема

```text
entity_revision_observation:
  entity_uid
  entity_version_id
  source_system
  source_revision_id       -- git: commit SHA; confluence: page version;
                            -- jira: changelog event ID либо composite
                            -- (issue_key + позиция изменения + время изменения,
                            -- с хешем payload для проверки идентичности
                            -- при ресинхронизации)
  provenance
  is_initial_baseline
```

Каждое появление состояния создаёт новую observation-запись; несколько observation для одной `entity_version_id` (revert, повторный crawl, параллельный scope) — норма.

`source_system` — идентификатор системы-источника, из которой получена сущность.

`provenance` — метаданные о происхождении observation: кто, когда, из какого источника и с помощью каких инструментов извлёк данные.


### 8. `entity_presence_observation` — базовая схема

Отсутствие сущности в snapshot — отдельный факт:

```text
entity_presence_observation:
  entity_uid
  snapshot_id
  presence_status   -- PRESENT | ABSENT_CONFIRMED | NOT_OBSERVED
                     -- | ACCESS_UNKNOWN | EXTRACTOR_GAP
  reason
  observed_at
```

`entity_revision_observation` создаётся только при `PRESENT`. Дальнейший  жизненный цикл в других ADR.

### 9. Публикация

```text
canonical_status ∈ {OBSERVED, EXTRACTED, QUALITY_REJECTED, CANONICAL_PUBLISHED}
```

Статус присваивается в рамках одного ingestion-прогона и финален: если предпосылки публикации объекта не выполнены, сущность не публикуется в этом прогоне — статус для той же `entity_version_id` может быть установлен только следующим идемпотентным прогоном.

### 10. Resolution pipeline

Версионирование сущностей происходит в два подхода.

Pass 1 — Version Pass:
1. вычисление content_hash;
2. сравнение content_hash с последним известным состоянием entity_uid;
3. создание/переиспользование entity_version_id;
4. создание entity_revision_observation.

Pass 2 — Provenance Pass
1. ожидаете выполнения Pass 1;
2. метаданные о происхождении по данному наблюдению объекта строятся по каждой ревизии, реально изменившей content_hash


### 11. Rename, move, split, merge, delete

1. `entity_uid` уже подтверждённой сущности не пересчитывается; решение о присвоении UID новому наблюдению — evidence-based. 
2. Split (одна сущность разделяется на две или больше) создаёт новые `entity_uid` со связью `SPLIT_FROM`.
3. Merge вводит `entity_redirect` (uid→uid), отдельный от `entity_alias` (key→uid); источник переводится в `RETIRED` и не может быть повторно выбран как target без явного redirect; операция проходит HITL. 
4. Delete предваряется различением `NOT_OBSERVED`/`EXTRACTOR_GAP` от подтверждённого отсутствия (`ABSENT_CONFIRMED`) перед передачей в retention.

### 12. Provenance для кода: Jira → ветка → коммит

Применимо только к коду. Иерархия evidence для issue attribution:

```text
1. явная Jira/PR интеграция
2. явная ссылка на issue key в commit message
3. соответствие имени feature-ветки шаблону
```

Связи: 
- `TOUCHED_IN` (коммит изменил файл/регион, независимо от изменения `content_hash`),
- `IMPLEMENTED_IN` (коммит создал новую `entity_revision_observation` И прошёл evidence выше `AMBIGUOUS`). 

Для Confluence и Jira отдельная provenance-цепочка не вводится — история наблюдений самой сущности достаточна.


## Последствия

### Положительные

- Единая модель identity для кода, Confluence и Jira с явным составом `content_hash` для каждого источника.
- `entity_uid` неизменен для подтверждённых сущностей; для Confluence/Jira резолюция преимущественно `CONFIRMED_BY_SOURCE`, что снижает нагрузку на HITL по сравнению с кодом.
- `entity_revision_observation`/`entity_presence_observation` разделяют наблюдение версии и подтверждённое отсутствие, не создавая ложных фактов.

### Отрицательные

- Состав `content_hash` для Jira зависит от policy, требующей сопровождения при изменении бизнес-процесса.
- Composite `source_revision_id` для Jira усложняет реализацию connector'а.
- Перенос Jira issue между проектами без исторической ссылки на старый key неизбежно уходит в `AMBIGUOUS`.

## Рассмотренные альтернативы

### `entity_uid` как прямая производная от `space_key + page_id` (без слоя `derived_key`)

**Минусы:** делает `entity_uid` не прозрачным, а вычисляемым из потенциально мигрирующего атрибута (space); при переносе между spaces потребовался бы пересчёт. Отклонено в пользу единого слоя `derived_key`/`entity_alias` для всех источников.

### Единая модель identity без source-specific `content_hash`

**Минусы:** невозможно корректно отразить структуру Confluence (макросы, таблицы, вложения) или batch-природу изменений Jira одной общей формулой. Отклонено.
