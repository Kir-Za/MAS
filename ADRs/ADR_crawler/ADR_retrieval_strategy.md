# ADR: Стратегия получения данных из Qdrant и Neo4j

**Статус:** Предложен

## Контекст

Qdrant и Neo4j хранят разные представления одной предметной области. Qdrant выполняет семантический и лексический поиск по фрагментам содержимого. Neo4j хранит сущности, связи, зависимости, источник и версионный контекст. Хранилища обновляются независимо и имеют конечную согласованность.

## Решение

Принять **адаптивный гибридный retrieval** с тремя режимами.

### 1. Маршрутизация запроса

Маршрутизация выполняется быстрым детерминированным классификатором по:
- наличию известных сущностей и идентификаторов;
- маркерам связей: «зависит», «связан», «произошёл из»;
- маркерам множественных переходов: «через», «цепочка», «между»;
- наличию явного graph-only намерения;
- продукту и версионированному scope.

Для неопределённых случаев может использоваться LLM-классификатор с ограниченным бюджетом. Если классификатор недоступен, ошибся или его уверенность ниже настроенного порога, используется параллельный режим.

### 2. Режимы retrieval

#### Обычный QA (запрос-ответ)

Qdrant выполняет hybrid dense+sparse поиск. Neo4j вызывается только для обогащения найденных сущностей, если это необходимо для определения источников, версий или локальных связей.

#### Явная сущность или relational-запрос

Neo4j выполняет поиск сущности и ограниченный по количеству переходов в графе. Найденные `entity_uid` используются для:
- получения связанных chunks из Qdrant;
- формирования ограниченного scope;
- обогащения результатов.


#### Неопределённый тип запроса

Qdrant и Neo4j выполняются параллельно.


### 3. Fusion

В параллельном режиме используется Reciprocal Rank Fusion. RRF объединяет позиции результатов, а не абсолютные значения scores, поэтому не требует калибровки semantic similarity и graph relevance.

Для запросов с явно указанной сущностью или авторитетным graph scope применяется детерминированный приоритет:
- результаты, непосредственно подтверждённые графом, размещаются выше;
- результаты Qdrant не исключаются, если не нарушают обязательные фильтры;
- при равном приоритете используется RRF или исходный порядок соответствующего источника.

Fusion выполняется retrieval-сервисом. Planner выбирает режим, но не реализует низкоуровневое объединение результатов.


### 4. Multi-hop

Planner отвечает за разложение multi-hop задачи и последовательность hop-ов. Retrieval-сервис выполняет атомарные операции:
- найти сущность;
- получить связанные сущности;
- получить chunks по `entity_uid`;
- выполнить поиск в заданном scope.

Каждый hop возвращает источник и ограничения следующего вызова. Retrieval-сервис не принимает самостоятельное решение о бесконечном продолжении traversal.

### 5. Идентификаторы

Связь Qdrant и Neo4j выполняется через:
- `entity_uid` — стабильную идентичность логической сущности;
- `entity_version_id` — идентификатор версии содержимого.

`entity_version_id` не используется как стабильный идентификатор сущности. Изменение содержимого создаёт новую версию, но не обязательно новую сущность.

### 6. Фильтрация

Обязательными hard-фilters являются:
- ACL;
- явно заданный продукт;
- явно заданная версия, ветка или release scope.

Если продукт или версионный scope не переданы, используется настроенный default scope, который явно указывается в источнике результата как `default`.


### 7. Eventual consistency

Retrieval не ждёт статуса `COMPLETED`.
Если Neo4j вернул сущность, но соответствующие chunks ещё отсутствуют в Qdrant, сущность возвращается только как metadata/candidate с отметкой `content_pending`; она не передаётся LLM как текстовый контекст.
Если Qdrant содержит chunk, но Neo4j ещё не содержит соответствующую связь, chunk возвращается с отметкой `graph_incomplete`. Отсутствие связи не считается доказательством отсутствия отношения.
Каждый результат содержит источник, revision context и freshness/consistency status.

## Последствия

### Положительные

- Обычные QA-запросы получают быстрый семантический поиск.
- Relational и graph-only запросы не ограничены top-k Qdrant.
- Неполнота Neo4j не приводит к молчаливой потере Qdrant-контекста.
- Не требуется сравнивать абсолютные scores разных хранилищ.
- Временная недоступность одной ветки приводит к деградации, а не к полному отказу.
- Multi-hop оркестрация отделена от низкоуровневого retrieval.
- Неполнота и рассинхронизация явно видны потребителю.

### Отрицательные

- По сравнению с безусловным Qdrant-first увеличиваются сложность, стоимость и число режимов.
- Intent-классификатор становится дополнительным компонентом и источником ошибок.
- Параллельный режим повышает нагрузку на оба хранилища.
- Для корректного fusion нужны единые правила дедупликации, provenance и version filtering.
- При отсутствии содержимого graph entity нельзя использовать как полноценный контекст.
- Eventual consistency сохраняет временные окна неполного результата.
- Пороговые значения, traversal depth, latency budgets и RRF-параметры требуют эксплуатационного владения и регулярной валидации.

## Рассмотренные альтернативы

### Безусловный Qdrant-first с graph-enrichment

Универсальная стратегия; используется как fallback и основной режим для обычного QA.

**Плюсы:**
- простая реализация;
- предсказуемая latency;
- низкая нагрузка на Neo4j;
- хорошо подходит для обычного QA.

**Минусы:**
- теряет graph-only результаты;
- не находит связи, если исходная сущность не попала в top-k Qdrant;
- плохо поддерживает multi-hop и структурные запросы.

### Graph-first retrieval
Универсальный режим; используется для явно структурных запросов.

**Плюсы:**
- хорошо подходит для relational и multi-hop запросов;
- естественно поддерживает traversal;
- позволяет искать по структуре независимо от лексики запроса.

**Минусы:**
- зависит от entity resolution и полноты графа;
- хуже работает с narrative/free-text запросами;
- может иметь высокую latency при traversal;
- способен молча потерять контент при неполном графе.

### Параллельный поиск всегда

Используется при низкой уверенности классификатора и для критичных запросов.

**Плюсы:**
- не требуется intent-классификатор;
- минимизируется риск неправильной маршрутизации;
- естественно поддерживает fusion и fallback.

**Минусы:**
- постоянная нагрузка на оба хранилища;
- выше средняя стоимость;
- сложнее выдерживать latency и capacity limits.

### Жёсткий graph-фильтр для Qdrant

Явно определенные сущности; для остальных случаев применяется как soft preference или источник кандидатов.

**Плюсы:**
- уменьшает количество кандидатов;
- может повысить precision при полном и актуальном графе;
- удобен для авторитетного scope.

**Минусы:**
- неполный или устаревший граф молча снижает recall;
- ошибка entity resolution исключает правильный контекст;
- сложно применять к свободным запросам.


### Раздельные retrieval API для каждого агента

Низкоуровневые специализированные API допускаются, но общий retrieval-сервис должен предоставлять единый контракт и политики.

**Плюсы:**
- максимальная гибкость для конкретного агента;
- независимое развитие сценариев;
- простой базовый контракт каждого хранилища.

**Минусы:**
- дублирование routing, fusion, version filtering и consistency-логики;
- расходящиеся правила между агентами;
- сложнее наблюдаемость и контроль безопасности.
