# ADR Разрешение идентичности ingestion-сущностей

**Статус:** Предложен

---

## Контекст и проблема

После контроля качества processing units с `quality_verdict=PASS` готовы к определению логической сущности. До этого этапа доступны:

- контекст источника;
- `source_object_id`;
- `source_revision_id`;
- `unit_source_anchor`;
- `content_hash`;
- структурные поля для кода;
- `structured_content`.

Разрешение идентичности должна выполняться только для units, прошедших контроль качества. `REJECTED` units не получают identity, а `QUARANTINED` units ожидают решения HITL и не участвуют в обычном разрешении идентичности.

Разные источники используют разные признаки идентичности:

- Git не предоставляет стабильный ID функции, класса или модуля;
- Confluence предоставляет `page_id`;
- Jira предоставляет `issue_key`;
- символы кода могут переименовываться, перемещаться, разделяться и объединяться;
- `derived_key` может изменяться, но `entity_uid` подтверждённой сущности не должен изменяться.

Qdrant и Neo4j должны получить одну и ту же разрешённую identity. Ни один из них не назначает `entity_uid` самостоятельно.

**Проблема:** как назначать или подтверждать `entity_uid` для качественных processing units, корректно обрабатывать source-specific identity и неоднозначность, не создавая ложных связей и не назначая identity непригодному контенту.

---

## Факторы решения

* Разрешение идентичности выполняется после контроля качества.
* Один processing unit должен получить одинаковый результат identity для RAG и Graph.
* `entity_uid` не должен зависеть от изменяемого имени, пути, ветки, коммита или содержимого.
* `derived_key` используется только как ключ-кандидат.
* `content_hash` используется как свидетельство, но не заменяет identity.
* Стабильные source-native идентификаторы должны использоваться там, где их предоставляет источник.
* Неоднозначная identity не должна приводить к автоматическому слиянию.
* `entity_version_id` создаётся только после разрешения `entity_uid`.
* Повторное обнаружение той же сущности должно переиспользовать её `entity_uid`.
* `REJECTED`, `QUARANTINED` и неразрешённая identity не должны попадать в обычную материализацию.
* `tenant_id`, метаданные ACL, Bamboo, `content_policy_version`, `content_version` и `crawl_mode` не используются.
* Семантическая близость не используется для назначения `entity_uid`. Страница Confluence и класс кода получают разные `entity_uid`, даже если их содержание семантически близко. Семантическая близость может использоваться только для формирования доменных связей между уже идентифицированными сущностями на этапе работы с графом.

---

## Решение

Мы выполняем разрешение идентичности как один логический этап:

```text
PASS ProcessingUnit
    ↓
Разрешение идентичности
    ↓
разрешённый entity_uid
или
UnresolvedIdentityRecord
```

Разрешение идентичности включает внутренний поиск кандидатов и принятие одного итогового решения. 

### 1. Вход разрешения идентичности

Разрешитель идентичности получает только processing units, для которых:

```text
quality_verdict = PASS
content_hash определён
source content доступен
```

Входной контракт:

```text
source_system
source_scope
source_object_id
source_revision_id
unit_source_anchor
content_type
source_container
structured_content
content_hash
raw_payload_checksum
observed_at
```

Для единиц кода дополнительно используются:

```text
repository_id
module_path
qualified_symbol
symbol_kind
signature_fingerprint
full_symbol_span_text
declared_interfaces_or_base_types
```

`parent_unit_id` используется только внутри in-memory IR и не участвует в разрешении идентичности как постоянный идентификатор.

Units со следующими состояниями не передаются в разрешение идентичности:

```text
quality_verdict = REJECTED
quality_verdict = QUARANTINED
source content недоступен
```

### 2. Поиск существующей identity

Разрешитель ищет соответствующую сущность в реестре идентичностей по:

- source-native identity;
- текущему `derived_key`;
- `entity_alias`;
- `content_hash`;
- структурным признакам;
- source-specific свидетельствам.

Порядок свидетельств зависит от `source_system` и `content_type`.

Разрешитель не использует:

- физические ID Qdrant;
- физические ID Neo4j;
- `snapshot_id` как identity;
- `source_revision_id` как `entity_uid`;
- `parent_unit_id`;
- семантическую близость для назначения `entity_uid`.

### 3. Source-specific identity

#### Git code

Для кода используется:

```text
derived_key =
  repository_id
  + module_path
  + qualified_symbol
  + symbol_kind
  + signature_fingerprint
```

`derived_key` является изменяемым ключом-кандидатом. Он может измениться при:

- переименовании;
- перемещении;
- изменении namespace;
- миграции или переименовании репозитория;
- изменении правил формирования ключа.

Если свидетельства подтверждают продолжение существующей сущности кода:

- сохраняется прежний `entity_uid`;
- прежний ключ регистрируется как `entity_alias`;
- новый `derived_key` становится текущим.

Если продолжение не подтверждено, новое наблюдение не связывается автоматически со старым `entity_uid`.

#### Confluence

Для страницы используется:

```text
derived_key = space_key + page_id
```

`page_id` является source-native identity страницы внутри области видимости Confluence.

Переименование или перемещение страницы внутри space при сохранении `page_id` не создаёт новую логическую сущность.

Миграция между пространствами или сайтами требует отдельного решения. Простого совпадения заголовка, иерархии или `content_hash` недостаточно для автоматического сохранения identity.

#### Jira

Для задачи используется:

```text
derived_key = issue_key
```

`issue_key` является source-native identity задачи Jira.

Перенос задачи между проектами со сменой `issue_key` сохраняет прежний `entity_uid` только при наличии source свидетельства о миграции. Без такого свидетельства создаётся неразрешённый случай identity.

### 4. Результаты разрешения идентичности

#### Разрешённая identity

Если существующая сущность подтверждена или создана по допустимому правилу:

```text
entity_uid
derived_key
identity_status
```

`identity_status` принимает значения:

```text
CONFIRMED_BY_RULE
CONFIRMED_BY_SOURCE
CONFIRMED_BY_HITL
```

`entity_uid`:

- глобально уникален;
- не зависит от ветки, пути, имени символа, коммита или хеша содержимого;
- не изменяется после подтверждения;
- не переиспользуется после вывода из эксплуатации;
- используется одинаково в Qdrant и Neo4j.

#### Неразрешённая identity

Если разрешитель не может надёжно определить identity:

```text
identity_status = AMBIGUOUS
entity_uid отсутствует
```

Создаётся `UnresolvedIdentityRecord`, содержащий:

```text
record_id
snapshot_id
ingestion_run_id
source_system
source_scope
source_object_id
source_revision_id
unit_source_anchor
content_hash
derived_key
identity_status
observed_at
created_at
```

Такая запись:

- не создаёт `entity_version_id`;
- не создаёт `EntityRevisionObservation`;
- не передаётся в разбиение на фрагменты;
- не передаётся в извлечение графа;
- сохраняется в хранилище неразрешённых идентичностей;
- может быть повторно разрешена после HITL или нового source свидетельства.

### 5. Правила принятия решения

Разрешитель применяет следующие правила:

1. Точное совпадение стабильной source identity подтверждает существующую сущность, если нет конфликта.
2. Совпадение текущего `derived_key` является сильным свидетельством продолжения сущности.
3. `content_hash` подтверждает совпадение состояния, но не является самостоятельным доказательством совпадения логической identity.
4. LSP references и история Git формируют свидетельства для родословной кода.
5. Отсутствие конкурирующего кандидата само по себе не является достаточным доказательством.
6. Наличие нескольких сопоставимых кандидатов приводит к `AMBIGUOUS`.
7. Автоматическое слияние существующих `entity_uid` не выполняется этим ADR; слияние и `entity_redirect` регулируются ADR-003.
8. Уже подтверждённый `entity_uid` не изменяется из-за нового низкоуверенного наблюдения.
9. Новая сущность может быть подтверждена по source/rule policy только при выполнении условий, определённых ADR-003.
10. Решение и использованное свидетельство должны быть пригодны для аудита.
11. Семантическая близость не используется как свидетельство для разрешения идентичности. Страница Confluence и класс кода всегда получают разные `entity_uid`.

### 6. Initial load

При initial load реестр идентичностей может быть пустым. Поэтому отсутствие найденного кандидата не означает автоматически, что identity подтверждена.

Для начального базового уровня:

- сущность получает `CONFIRMED_BY_RULE` только при выполнении условий ADR-003;
- выставляется `is_initial_baseline=true` на этапе финализации версий;
- символы с неполным происхождением, неподдерживаемыми конструкциями или недостаточными свидетельствами получают `AMBIGUOUS`;
- результаты initial load оцениваются на golden dataset до production publication.

### 7. Передача результата

Для разрешённой identity разрешитель передаёт в финализацию версий:

```text
entity_uid
derived_key
identity_status
content_hash
source context
provenance
```

Финализация версий затем вычисляет:

```text
entity_version_id = hash(entity_uid + content_hash)
```

и создаёт `EntityRevisionObservation`.

Для неразрешённой identity передаётся:

```text
UnresolvedIdentityRecord
```

Без создания `entity_version_id` и `EntityRevisionObservation`.

### 8. Идемпотентность

Повторное разрешение одного и того же source наблюдения не должно создавать новый `entity_uid`, если свидетельства identity и source identity не изменились.

Идемпотентность обеспечивается сочетанием:

```text
source_system
source_scope
source_object_id
source_revision_id
unit_source_anchor
```

и проверкой существующего реестра идентичностей.

`entity_uid` не вычисляется из `snapshot_id` и не меняется при повторном обходе.

### 9. Границы ответственности

Разрешение идентичности отвечает за:

- поиск существующей identity;
- вычисление `derived_key`;
- назначение или переиспользование `entity_uid`;
- установку `identity_status`;
- регистрацию псевдонимов;
- создание `UnresolvedIdentityRecord`;
- передачу разрешённой identity в финализацию версий.

Разрешение идентичности не отвечает за:

- вычисление `content_hash`;
- контроль качества;
- создание `entity_version_id`;
- создание `EntityRevisionObservation`;
- разбиение на фрагменты;
- встраивание;
- извлечение графа;
- материализацию в Qdrant/Neo4j;
- финальное применение связей семантической родословной;
- слияние и `entity_redirect`, за исключением вызова соответствующей логики ADR-003;
- формирование семантических доменных связей на основе семантической близости — это ответственность модуля работы с графом.

## Инварианты

1. Разрешение идентичности выполняется только после контроля качества.
2. В разрешении идентичности участвуют только units с `quality_verdict=PASS`.
3. `REJECTED` и `QUARANTINED` units не получают `entity_uid`.
4. `entity_uid` назначается только каноническим разрешителем идентичности.
5. Qdrant и Neo4j получают один и тот же `entity_uid`.
6. `entity_uid` не вычисляется из `snapshot_id`, source revision, ветки, пути, имени символа или `content_hash`.
7. `derived_key` используется только внутри разрешения идентичности.
8. `derived_key` может изменяться без изменения подтверждённого `entity_uid`.
9. `content_hash` является свидетельством, но не заменяет логическую identity.
10. Отсутствие кандидата не является достаточным основанием для подтверждения identity.
11. Неоднозначная identity получает `identity_status=AMBIGUOUS`.
12. Неразрешённая identity сохраняется в `UnresolvedIdentityRecord`.
13. Для неразрешённой identity не создаются `entity_version_id` и `EntityRevisionObservation`.
14. `entity_version_id` создаётся только после назначения `entity_uid` на этапе финализации версий.
15. Слияние и `entity_redirect` регулируются ADR-003.
16. Повторное разрешение одного source наблюдения идемпотентно.
17. `entity_uid` не переиспользуется после вывода из эксплуатации.
18. Разрешение идентичности не изменяет `content_hash`.
19. Разрешение идентичности не записывает данные в Qdrant или Neo4j.
20. `tenant_id`, метаданные ACL, Bamboo, `content_policy_version`, `content_version` и `crawl_mode` не используются.
21. Семантическая близость не используется для назначения `entity_uid`. Страница Confluence и класс кода получают разные `entity_uid`.

## Новые переменные

| Переменная | Тип | Описание | Точка появления |
|---|---|---|---|
| `entity_uid` | `uuid` | Глобально уникальный идентификатор логической сущности | Канонический разрешитель идентичности |
| `derived_key` | `string` | Source/type-specific ключ-кандидат для поиска identity | Канонический разрешитель идентичности |
| `identity_status` | enum | Результат разрешения идентичности: `CONFIRMED_BY_RULE`, `CONFIRMED_BY_SOURCE`, `AMBIGUOUS`, `CONFIRMED_BY_HITL` | Канонический разрешитель идентичности |
| `UnresolvedIdentityRecord` | структура | Постоянная запись PASS unit с неразрешённой identity | Канонический разрешитель идентичности |
| `record_id` | `uuid` | Идентификатор `UnresolvedIdentityRecord` | Канонический разрешитель идентичности |
| `is_initial_baseline` | `boolean` | Признак identity, подтверждённой в рамках initial load | Финализация версий |

## Последствия

### Положительные

* Разрешение идентичности выполняется только для качественных units.
* `entity_uid` единообразен для Qdrant и Neo4j.
* Изменение `derived_key` не разрывает подтверждённую identity.
* `content_hash` используется как свидетельство, но не подменяет логическую identity.
* Неразрешённые случаи не теряются после удаления временного снимка.
* `entity_version_id` создаётся только после завершения разрешения идентичности.
* Initial load не подтверждает сущности автоматически только из-за пустого реестра.
* Слияние и `entity_redirect` не дублируются в этом ADR.
* Повторное разрешение identity идемпотентно.
* Source-specific правила Git, Confluence и Jira не смешиваются.

### Отрицательные

* Неразрешённые identity требуют хранения `UnresolvedIdentityRecord`.
* HITL или дополнительные source свидетельства могут задержать публикацию сущности.
* Ошибка разрешителя идентичности может создать неверное постоянное сопоставление.
* Поддержка переименования, перемещения и миграции требует source-specific свидетельств.
* Initial load и разрешение identity кода требуют отдельной оценки качества.
* Для разных типов сущностей необходимы разные политики разрешения.
* После изменения решения identity может потребоваться повторная обработка downstream материализаций.

## Рассмотренные альтернативы

### Выполнять разрешение идентичности до контроля качества

Сначала назначать `entity_uid`, затем проверять качество content unit.

**Плюсы:**

* identity доступна всем последующим этапам;
* проще связать quality result с entity;
* rejected content сразу имеет source identity.

**Минусы:**

* разрешение идентичности выполняется для пустого, повреждённого и неподдерживаемого контента;
* создаются identity records, которые не будут материализованы;
* усложняется откат ошибочных решений;
* возрастает стоимость приёма данных;
* повышается риск закрепить ложную identity на некачественном входе.

**Решение:** отклонено. Контроль качества выполняется до разрешения идентичности.

### Использовать `content_hash` как `entity_uid`

Назначать логическую identity на основе нормализованного содержимого.

**Плюсы:**

* детерминированная генерация;
* простая точная дедупликация;
* не требуется отдельный реестр идентичностей для первоначального сопоставления.

**Минусы:**

* изменение содержания меняет identity;
* разные сущности с одинаковым содержимым получают один UID;
* переименование и перемещение не отслеживаются;
* source context и логическая identity смешиваются.

**Решение:** отклонено. `content_hash` используется как свидетельство и идентификатор состояния содержимого.

### Использовать `derived_key` как постоянный `entity_uid`

Назначать identity напрямую из репозитория, пути, полного имени символа и сигнатуры.

**Плюсы:**

* простой поиск;
* не требуется отдельная генерация непрозрачного UID;
* удобно для первичной реализации.

**Минусы:**

* переименование, перемещение и миграция меняют identity;
* история сущности разрывается;
* изменение правил формирования ключа создаёт новые UID;
* возрастает риск дубликатов.

**Решение:** отклонено. `derived_key` является изменяемым ключом-кандидатом.

### Создавать новый `entity_uid` для каждого наблюдения

Каждое source наблюдение получает новый UID.

**Плюсы:**

* простая реализация;
* отсутствует риск ошибочного сохранения identity;
* наблюдения легко изолировать.

**Минусы:**

* теряется identity сущности во времени;
* невозможно корректно отслеживать переименование и перемещение;
* растёт число дубликатов;
* сложнее извлечение графа и исторический поиск.

**Решение:** отклонено. Повторные observations используют существующий `entity_uid`, если identity подтверждена.

### Всегда направлять неопределённые случаи в HITL

Любое отсутствие точного совпадения или недостаток свидетельств блокирует автоматическую обработку.

**Плюсы:**

* минимальный риск автоматического ложного слияния;
* решения легко объяснить;
* высокая осторожность при миграции и переименовании.

**Минусы:**

* высокая нагрузка на операторов;
* низкая масштабируемость;
* задержка обработки большинства новых сущностей;
* излишний HITL для source-native identity и детерминированных случаев.

**Решение:** отклонено как общий режим. HITL используется для `AMBIGUOUS` и определённых политикой высокорисковых случаев.

### Использовать семантическую близость для разрешения идентичности

Сопоставлять страницы Confluence и код по смыслу текста.

**Плюсы:**

* можно связать документацию и код без явных ссылок;
* автоматическое обнаружение семантических связей;
* потенциально выше полнота для cross-source связей.

**Минусы:**

* семантическая близость не является доказательством идентичности;
* ложные срабатывания создают неверные `entity_uid`;
* слияние разных сущностей на основе смысла опасно;
* документация и код — это разные аспекты одной предметной области;
* семантическая близость лучше подходит для доменных связей, а не для identity.

**Решение:** отклонено. Семантическая близость запрещена для разрешения идентичности. Страница Confluence и класс кода всегда получают разные `entity_uid`.
